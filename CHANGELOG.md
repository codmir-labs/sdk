## Unreleased

### ⚠ BREAKING CHANGES

* **exports:** the package no longer exports `./serverless`, `./council`, `./runtime`, `./runtime/protocol`, `./agent`, `./mcp` and `./ai`. They were removed in 2.1.0 without a major release, so an app on `^2.0.1` that imports one of them fails with `ERR_PACKAGE_PATH_NOT_EXPORTED` after `npm update`. None of them has a published replacement: the code is no longer published. Remove the import, or stay on 2.0.1. `@codmir/sdk/overseer`, `/tracing` and `/replay` are unchanged. See [MIGRATION_GUIDE.md](MIGRATION_GUIDE.md#2x-to-30).

### Features

* **browser, nextjs, remix:** every browser entry records the same breadcrumbs. `@codmir/sdk/browser` recorded no route changes, and `/nextjs` and `/remix` recorded no clicks, `fetch` or XHR, so the README's promise held for none of them. One installer now serves all three: clicks (`trackClicks`, on), inputs (`trackInputs`, off), `fetch` and XHR (`trackRequests`, on), route changes (`trackNavigation`, on; `trackRouteChanges` and `captureRouteChanges` keep working as its older names) and, new, console output (`trackConsole`, default `['error', 'warn']`; `true` is that default, `false` is off, or list `'info'`, `'log'`, `'debug'`). A console breadcrumb has the category `console`, a level that matches the method, the arguments joined, scrubbed of secrets and cut to 200 characters; a message identical to the newest breadcrumb raises its `data.count` instead of adding one, so a loop of warnings cannot push the rest out of the 20 an error keeps. It works with `captureConsoleErrors` whichever patches `console` first, and `close()` puts `console` back. `addRepeatedBreadcrumb(crumb)` is public beside `addBreadcrumb()`: a crumb identical to the newest (same category, level and message) raises that one's `data.count` instead of adding another. A page's first `/browser` `init` now starts its trail with a `navigation` breadcrumb for the page.
* **feedback:** a visitor reads what became of their feedback and says whether the fix helped. `feedbackStatus(id, reporterToken?)` resolves `{ ok: true, state: 'received' | 'known' | 'fixed', release, fixedAt, reply, answer }` (the last four are `null` unless fixed) and `answerFeedback(id, better, reporterToken?)` sends `{ better }` and resolves the same. Both use the stored token on a page and only a given one on a server, never throw, never change the stored receipts (a `404` may be an older server), check every field of the answer, and send only the key, the token, the id and one boolean in headers and body: no cookie, no `keepalive`, no retry, no timer, no breadcrumb, span or `traceparent`, and never a token in a URL. New reasons: `not_found`, `not_fixed`; `refused` and `rate_limited` as for `sendFeedback`. Two `feedbackStatus` calls in flight for the same entry on a page are one request; answers go out in order, never merged. `/feedback` grows by 0.7 kB gzip. The answer limit rises to 8 KB. See `examples/feedback`.
* **feedback:** `@codmir/sdk/feedback` sends what an app's visitors say with the session it is about. `sendFeedback(text | { text, replyWhenFixed, replayId, eventId, failedRequest, pagePath, userId, storage, timeoutMs })` posts to the server's feedback door and adds, from the client `init()` made, the replay id, the id of the last error captured in the last 10 minutes, the newest failed request of the last 5 minutes to the page's own origin or a `tracePropagationTargets` match (never one of the SDK's own), the page path (never a query, fragment or origin), the environment, the release, `user.id` (never the email or name) and the SDK's version; what you pass wins and `false` switches one off. It never throws, resolves `{ ok, id, reporterToken, known }` or `{ ok: false, reason }` (`not_configured`, `empty`, `too_long`, `unauthorized`, `payment_required`, `rate_limited`, `refused`, `unavailable`), makes no breadcrumb, span, `traceparent` or cookie of its own, times out after 10 seconds and never retries; the same text in flight is one request. `deleteFeedback` and `listFeedback` use a receipt (id, token, time, never the text) kept in `localStorage` or memory. On a server, where one client serves every visitor, only what is passed is sent beside the environment and the release, nothing is kept and no calls are merged. No UI component. See `examples/feedback`.
* **express, nextjs, hono:** an error captured while a handler serves a request carries `request.url` (origin and path, never the query) and `request.method`. The request rides AsyncLocalStorage next to the tracing context, so concurrent requests never see each other's; an error outside any request has none. Express: `requestHandler`, `errorHandler`, `tracingHandler`; Next.js: `withCodmirTracing`, `withCodmirMiddleware`, `captureRequestError`, `captureRouterError`; Hono: `codmirTracing`. Headers, cookies and body are never put in `event.request`.
* **overseer:** `captureException` sends where the error happened: `contexts.browser`/`os`/`device` in a browser (from `navigator.userAgentData`, else a userAgent parse), `contexts.runtime`/`os` in Node, and in a browser `request.url` as origin and path only (never the query, hash, headers, cookies or body). In Node the first three in-app frames carry `pre_context`/`context_line`/`post_context` (5 lines each side, 240 characters per line, files over 1 MB skipped; turn off with `includeSourceContext: false`). Needs Node 20.16 or 22.3+ for ES modules (`process.getBuiltinModule`) to read the OS release and source files; CommonJS works on any supported Node.
* **logs:** `@codmir/sdk/logs` finds what is wrong in an app's own logs, on the app's machine with no account and no network. `createLogMonitor()` takes log lines (`record`) and served requests (`request`), keeps nothing raw (emails, IP addresses, tokens, JWTs, `token=` pairs, query strings and user agents are redacted before anything is stored, and `redact(redact(x))` equals `redact(x)`), groups them (a message with its numbers, ids, dates and quoted values folded, a JSON line or an object by its message; a request by method, path pattern and status; 500 groups at most), and every 15 minutes judges each group `new`, `alarm`, `back`, `known` or `noise`, with its last 96 batch counts. `@codmir/sdk/logs/node` adds `captureConsole`, `captureProcess` (uses `uncaughtExceptionMonitor`, so Node still prints the stack and exits with code 1), `fileSink` (JSON lines, mode 0600, rotated at 5 MB), and `expressLogs` and `honoLogs` middlewares. With `cloud: true` or `cloud: { apiKey }` each finding is sent as one issue through the SDK's own client, once an hour at most, at once when it is back, with the hits since its last send, capped at 50 per batch and 1,000 per day. Off by default. See `examples/log-findings`.

### Bug Fixes

* **navigation:** a hash router's pages are no longer lost, and a token never rides in a fragment. `scrubUrl` dropped every fragment, so Vue's hash mode or `createHashHistory` logged the bare origin on every navigation breadcrumb, sent `/` as `request.url`, and never started a browser-tracing `navigation` transaction, which compared only the pathname. A fragment that starts with `#/` or `#!/` is now kept, cut at its own `?`; every other one (`#access_token=…`, `#id_token=…`, `#section-2`) is still dropped. Navigation breadcrumbs, `request.url` and the other scrubbed URLs carry the route fragment, and a change of path or route fragment starts a `navigation` transaction.
* **nextjs:** `captureRouterTransitionStart(route)` put the route unchanged in the breadcrumb, and Next.js 15.3's `onRouterTransitionStart` hands it the full href, so `/reset?token=…#access_token=…` reached the event body against the README's promise. The route now goes through `scrubUrl`, against the page's address: a path stays a path, an absolute URL stays absolute, the query goes, and a fragment stays only if it is a route. The README shows the `instrumentation-client.ts` wiring.
* **replay:** meta tags that carry a token are never recorded. Hidden inputs were masked, but the same token in `<meta name="csrf-token" content="…">` (the Rails and Laravel default), `<meta name="_csrf">` (Spring Security) or a nonce meta was uploaded in every full snapshot. The recorder now drops the tags rrweb lists as verification metas (`csrf-token` and `shopify-checkout-api-token` among them), and the SDK's own filter sets `content` to an empty string on every `<meta>` whose `name`, `property` or `http-equiv` has a part, split on anything but letters, that is `csrf`, `xsrf`, `token`, `nonce`, `secret` or `key` (`_csrf`, `x-csrf-token`, `csp-nonce`, `google-maps-api-key`; not `keywords`, `description` or `viewport`), in a full snapshot, in a meta added later, and in a change of its `content` or of the `name` that makes it one. Every other meta is recorded as before.
* **install:** `next`, `react` and `react-native` are no longer peer dependencies. No file of the package loads them, and npm 7 and later checked their ranges whenever an app had them, so an app on React 17, Next.js 13 or 14, or React Native 0.71 could not install the SDK without `--legacy-peer-deps`. `hono` stays an optional peer.
* **nextjs:** the README says Next.js 15 or later for server errors, because 14 never calls `onRequestError`, even with `experimental.instrumentationHook` on. CI now starts an app and proves that a server error is sent, on Next.js 15.0.0 and on the example's Next.js.
* **replay:** a busy server or an offline browser delays segments instead of losing them. An upload that failed was retried once, 1 s later, then lost, and a 429 (the server's 60 second rate window) was retried inside the same window and ignored `Retry-After`, so every busy minute or short outage cost a segment and a fresh snapshot. A 429 is now waited out for its `Retry-After` (seconds or an HTTP date, between 1 second and 10 minutes; 60 seconds when there is none). A network error, 5xx or 408 is still retried once at once, and a second failure puts the segment in a queue of at most 10 segments or 5 MB, kept in arrival order across replays and in sequence order within one, so a new segment never goes ahead of a queued one. The queue outlives a new replay id and `stop()`, so the replay of an error is still sent after its post-error window, and a segment is given up after 6 attempts from the queue, so a queue that never succeeds ends by itself. The queue sends one request at a time after the server's delay or a backoff that starts at 5 seconds, doubles to 5 minutes and starts over once a segment is stored, never while `navigator.onLine` is `false` (it checks again on its own timer), and at once on the `online` event unless the server asked for the wait. A queue that would overflow is dropped, each replay in it as one lost segment, so the fresh snapshot (3 at most) takes over. A segment flushed as the page hides is still sent once with `keepalive`, never queued. `UploadOutcome`, which gains the retry outcome, is internal: the replay entry does not export it.
* **replay:** a replay stays playable after a lost segment. A session recorded one full snapshot, in its first segment, so when that segment never arrived (the page was offline at the first 30 second tick, the upload failed twice, or the snapshot was over the request limit and dropped while the rest went up) every later segment was uploaded and billed and none could be played. A session now takes a snapshot every 5 minutes (`SESSION_CHECKOUT_MS`), and a segment whose upload fails, or a single event the server refuses as too large, is followed by a fresh one: the events recorded since are discarded and the next segment starts with Meta and FullSnapshot, at once, or while `navigator.onLine` is `false` on the `online` event or the first flush back online, one snapshot however many segments were lost, and at most 3 of them with no segment stored in between (after that the recorder drops what it records until the next periodic snapshot, so a wrong key or an outage costs no extra serialisation). In on-error mode a loss in the post-error window is recovered the same way and a loss while buffering needs nothing, as each buffer opens with its own snapshot. A FullSnapshot over the budget of one request now ends the replay in every mode: nothing of that segment (not the Meta, not the incremental events) is uploaded or handed to `onSegmentReady`, recording stops and `upload.debug` prints one line.
* **overseer:** URLs keep origin and path only, whatever their shape. `fetch` and XHR breadcrumbs kept `user:password@` in a protocol-relative URL or one with leading whitespace, a failed `fetch`'s error text (`data.error`) carried the whole URL with credentials and query, a `data:` URL was kept whole (`fetch(canvas.toDataURL())` made an 80 kB breadcrumb that pushed older ones out of an event), and `blob:` and `about:` URLs came out garbled. `scrubUrl` now trims its input, drops credentials when it falls back to cutting at `?` or `#`, and returns `data:image/png;base64,[80000 bytes]`, `blob:https://app.example.com/1d2e3f`, `about:blank`, and only `javascript:` or `mailto:` for other schemes without `//`; a result is at most 1,024 characters (`MAX_URL_LENGTH`). `fetch` and XHR resolve a protocol-relative URL against the page, and every URL in a failed fetch's error text is scrubbed the same way, after the request's own URL as the app passed it (a relative `/x?t=1` too) is replaced by its scrubbed form. A request's span keeps `url` as origin and path for a URL with a host, and the scrubbed form only for `data:`, `blob:` and `about:`. The trimming of trailing punctuation from a URL in free text is linear, so a URL of 200,000 dots cannot stall the page.
* **transport:** a DSN with a trailing slash sends to the same endpoints as one without. `https://www.example.com/api/v1/overseer/` built `…/overseer//ingest` (and `//replay`, `//patches/manifest`), which the server answers with a redirect; a browser on another origin sends a preflight first, and a preflight that is redirected fails, so every error and replay from such a page was lost with no message (Node follows the redirect, so servers were not affected). Every endpoint URL is now built from one base, the DSN without a trailing `/ingest` and trailing slashes, so `…/a`, `…/a/`, `…/a//`, `…/a/ingest` and `…/a/ingest/` all send to `…/a/ingest`, `…/a/replay`, `…/a/feedback` and `…/a/patches/manifest`.
* **remix:** a thrown redirect or 404 is passed on, not reported as an error. `wrapLoader` and `wrapAction` captured everything thrown, so the standard `throw redirect('/login')` auth guard made every signed-out visit an event titled `Error: [object Response]`. A thrown `Response` (or anything shaped like one) is now rethrown unchanged and captured only with a status of 500 or more and `captureResponseErrors` on, as `Response Error: <status> <statusText>` with `responseStatus` and `responseStatusText`. `handleError` follows the same rule: it used to capture a 3xx or 4xx `Response` too, and now ignores it. A 5xx object seen by a wrapper and then by `handleError` is sent once, and so is any thrown object: an `Error` that `wrapLoader` or `wrapAction` sent was sent a second time when Remix handed the same object to `handleError`, so every loader or action error in an app using both was two events; one set of sent objects (shared by two copies of the module) now marks what a wrapper or `handleError` sends, and `handleError` skips a marked object. A thrown string or other non-object cannot be marked and is unchanged. A 5xx `Response` from `wrapAction` carries `formDataKeys`, like an error.
* **tracing:** the SDK skips only its own endpoints, not the rest of the DSN's origin. The rule skipped every request to the DSN's origin under its path, so with a DSN at the root of an origin every request of the app to it (such as `fetch('/api/cart')` behind a same-origin proxy) had no breadcrumb, no span and no `traceparent`, and a failed one was never offered as `failedRequest` to feedback; an app that monitors itself with a DSN such as `https://www.example.com/api/v1/overseer` lost its own `/api/v1/overseer/issues` calls the same way. A request is now the SDK's own only when it is on the DSN's origin at `<base>/ingest`, `<base>/replay`, `<base>/patches/manifest`, `<base>/feedback` or `<base>/feedback/<anything>`, the query never mattering. One module, `src/endpoints.ts`, builds those URLs and every caller uses it; the URLs themselves are unchanged.
* **tracing:** the SDK's own requests, replay uploads included, are not app breadcrumbs or spans. Only the ingest URL and `<base>/feedback` were left alone, so every replay segment upload (about every 30 seconds) became a `fetch` breadcrumb and an `http.client` span. Every request to the DSN's origin under its base path (errors, replay, feedback) is now skipped by `fetch` and XHR instrumentation, and `sendFeedback` uses the same rule to skip them when it picks the failed request.
* **overseer:** an error carries its last 20 breadcrumbs, and navigation, `fetch` and XHR messages name the path and the status. The SDK sent up to 100 breadcrumbs and the server keeps the last 20, so 80 were sent for nothing; `addBreadcrumb` now keeps 20. `pushState`, `replaceState` and `popstate` breadcrumbs read `pushState /checkout` (the path after the move, no query or fragment) instead of the bare method, and `fetch` and XHR breadcrumbs read `GET /api/cart 500`, or `GET /api/cart failed` with no answer, instead of the full scrubbed URL (`data` is unchanged).
* **overseer:** on a server the conversation id and the session id belong to the request. `setConversationId` and `setSessionId` wrote two fields of the one client, so with two requests in flight one request's conversation id landed on another's error and a batch carried the session id of whichever request set it last. Inside a request they now set that request's own ids, which its errors carry in `extra` and `contexts`; outside any request (a browser, React Native, a server outside a request) they write the client's, as before. A batch's `sessionId` is always the client's, never a request's, so on a server it is `null` unless one was set outside any request.
* **express:** 4xx errors are not sent unless `shouldHandleError` says so. `errorHandler()` captured every error it received, so any anonymous client could create a billed event and an issue with malformed JSON (a 400 from the body parser), an unknown path behind `next(createError(404))` or a 401 from auth middleware. It now sends an error only when it has no HTTP status or a status of 500 or more (read from `status`, `statusCode`, then `output.statusCode`, an integer from 100 to 599). `errorHandler({ shouldHandleError: (error, req, res) => boolean })` replaces that rule, and every error is still passed on with `next(err)`; the transaction's status and the request breadcrumb are unchanged. An app that relied on 4xx errors being reported passes a `shouldHandleError` that returns `true` for them.
* **express:** an event captured in a route has the signed-in user. `extractUser` ran when `requestHandler()` ran, before an auth middleware set `req.user`, so `captureException` in a route handler sent no user; only `errorHandler()` looked again. An event captured in the request now runs `extractUser` again when `req.user` has changed since the last run (once per change, not once per event), and a user set with `setUser` in the request still wins.
* **overseer:** the release and the environment come from the host when the app sets neither. Every event said `release: unknown` and `environment: development` unless `init` was given both, so a production app's errors were filtered as development and had no release to reopen against. The release is now the first set of `CODMIR_RELEASE`, `VERCEL_GIT_COMMIT_SHA`, `RAILWAY_GIT_COMMIT_SHA`, `RENDER_GIT_COMMIT`, `SOURCE_VERSION`, `CF_PAGES_COMMIT_SHA`, `COMMIT_REF` and `GITHUB_SHA`, and the environment the first set of `CODMIR_ENVIRONMENT`, `VERCEL_ENV` and `NODE_ENV`; an explicit option always wins, nothing is read where `process` is missing, `@codmir/sdk/nextjs` in a browser also reads `NEXT_PUBLIC_VERCEL_GIT_COMMIT_SHA` and `NEXT_PUBLIC_VERCEL_ENV`, and `debug: true` logs once when the release stays `unknown`. An app that ran with `NODE_ENV=production` and no `environment` now reports `production` instead of `development`.
* **nextjs:** an error caught by an error boundary reaches Codmir. In a production build Next.js hands an error caught by `app/error.tsx`, `app/global-error.tsx` or the Pages Router's `_error` to `console.error` only, so the browser handlers never saw it. `captureBoundaryError(error, info?)` (for `app/error.tsx` and `app/global-error.tsx`) sends it as an unhandled error with the mechanism `nextjs-error-boundary` and Next's `error.digest` as the tag `digest`, and `captureUnderscoreErrorException(ctx)` (for `pages/_error.js`) sends `ctx.err` with the request's method and path, no headers and no query, nothing for a 404 with no error, and on a serverless runtime resolves after the send. `captureRouterError` and `captureRequestError` send `error.digest` as the tag `digest` too, so a server error and its client report match. One Error object is sent once across `onRequestError`, `_error`, the error boundaries and the window handlers, whichever gets it first (a Pages Router render error reaches `onRequestError` and then `_error`, and the first keeps its `routerKind`, `routePath` and `routeType`); the record of sent errors lives in a `Symbol.for` slot on `globalThis`, so two copies of the SDK in one process share it. See the Next.js guide in the README.
* **overseer:** a group is keyed on where the error is, not on its line or its message, and the old key travels beside it. The fingerprint held the first in-app frame's `file:line` and the masked message, so any deploy that edited a line above a recurring throw made the same bug a new issue, ticket and fix; one bug split into one issue per engine's wording (Chrome, Firefox, Safari and Hermes say it four ways) and per user input (emails, URL slugs, quoted values, cuid, nanoid and `cus_` ids, short hashes, JWTs, dates); and it split again per host, per cache-busting query, per install or OS user, per release directory and per content-hashed bundle name. The fingerprint is now the error type, the first 3 in-app frames as `<file>:<function>` and, when there are `causes`, the root cause's type. The file is normalized for the key only: an http(s) URL keeps its path, `file://` and Hermes' `address at ` are dropped, the iOS app container, Android app-data directories and `app.asar/` become `app:///`, a Node path inside `process.cwd()` at `init()` is relative to it, `/releases/<id>/` collapses, and a content hash before the extension is removed (`main.3f2a9c1e.js` is `main.js`; `index-header.js` is kept). A function name loses `async `, `new `, `[as x]`, receivers such as `Object.` and `Module.`, and Firefox's `promise callback*`; an anonymous one is its source line, else its line number. With an in-app frame the message is not in the key; an error with none keeps it, folded like a log line (quoted values, dates, durations, short hashes, numbers, emails, URL paths). The key before this release is sent as `group.legacyFingerprint`, so the platform can attach a new event to an issue created before it; an app's own `fingerprint` from `beforeSend` still wins and sends no legacy key. Every issue regroups once under the new key. A frame whose function a minifier mangled (1 or 2 characters, or 3 deep in a one-line bundle) keys as its file alone and the folded message joins the key, so a redeploy that renames the functions keeps the group; a Rollup or Vite hash such as `index-Dx_9lC-p.js` and `.chunk.js` names (`main.3f2a9c1e.chunk.js`) are normalized too.
* **overseer:** an error's `cause` chain and an `AggregateError`'s `errors` are sent, and wrapped errors group by their root cause. Only the thrown error itself was sent, so `new Error('could not load the cart', { cause })` hid the refused connection behind it, every root cause behind one wrapper line was one issue, and every `Promise.any` failure (an `AggregateError` with no frames) was one issue. The event now carries `exception.causes` (`{ type, value, stacktrace?, source, parent }`, breadth first, cycle-safe, at most 5 deep, 10 inner errors per `AggregateError` and 10 entries, 30 frames each, messages scrubbed like the top one's, visible to `beforeSend`). The fingerprint of an error with causes takes its frame and message from the first cause with an in-app frame when the error has none, and gains a last part, the root cause's type: wrapped errors and `Promise.any` failures regroup once; errors without a cause keep their fingerprint.
* **overseer:** the culprit is the frame the fingerprint uses, and a cause's frames use the same app origins. The culprit was the first frame with a file, so an error thrown from a library or an engine call named that frame, not the app frame the group is keyed on; and `exception.causes` frames were parsed without the init caller's origin and `inAppOrigins`, so on a CDN-served page the inner errors of a `Promise.any` failure counted as third-party while the top error's did not. The culprit is now the first in-app frame of the top error, else of the first cause that has one, else the top error's first frame with a file, else the first cause's; a frame with no line prints as `file`, never `file:undefined`. Issues whose first frame was not an app frame get a new culprit, and CDN-origin causes regroup once.
* **overseer:** extension and third-party origin frames are not app code. Any frame without `node_modules` in its path counted as app code, so a `chrome-extension://` (or `moz-extension:`, `safari-extension:`, `safari-web-extension:`) frame, a tag manager's script on another origin, or a Deno `ext:` frame became the fingerprint's frame and the culprit; an extension that wraps `fetch` owned the app's `Failed to fetch` group. Extension schemes and `ext:` are now never `in_app`. In a browser an http(s) frame is app code only on the page's origin, the origin of the code that called `init()` (so a bundle served from a CDN keeps its frames) or an origin in the new `inAppOrigins` option; in Node, workers with no http(s) location and React Native only the first rule and the `node_modules` rule apply. The culprit is now the first app frame, else the top frame. Issues that had one of these frames as their location get a new fingerprint once; an app whose scripts sit on an origin that is neither the page's nor `init()`'s should set `inAppOrigins`.
* **overseer:** an engine frame with no file and line is not an app frame. V8's `at async Promise.all (index 0)` was read as an app file called `index 0` with no line, and became the fingerprint location, so two routes awaiting `Promise.all` merged into one issue, `index 0` and `index 1` split, and a plain `await` of the same call grouped on the app file. A frame whose location is not `file:line[:col]` (`index N`, `native`, `<anonymous>`, `[native code]`, a wasm position) now keeps its function, has no `filename`, and is never `in_app`; the fingerprint then takes the next app frame. Issues that had one of these as their location get a new fingerprint once.
* **replay:** mask and block hold inside open shadow roots and same-origin iframes. The recorder carried `[data-private]` and `[data-codmir-block]` into them only in the first snapshot, so text added or changed later in a shadow root or an iframe under a masked element was recorded in clear, what a blocked web component rendered later was recorded under its placeholder, and the document of a blocked `<iframe>` was recorded whole. A new filter after the recorder now tests the selectors on the composed ancestors of every added or changed node (a shadow root's host, an iframe's element), masks the text or drops the add, and drops what is attached under a blocked iframe; a node it cannot find is kept as recorded. The same filter also drops the attribute changes and the input, mouse, scroll and media events of a node under a block, which the recorder drops itself only in the light DOM.
* **replay:** upload budgets count UTF-8 bytes, and a refused segment is split. A segment was sized in string length, but the server limits bytes, so near the budget a page that is more than about 8% Chinese, Japanese or Korean text sent a body over 2 MB, got a `413` and lost the segment; and a segment of 60 to 165 KB of UTF-8 left with `keepalive` over the browser's 64 KiB quota. Both now use bytes. A `413` is no longer final: the segment is cut in two and each half is sent (the second under the next segment number of that replay, with the error ids), and one event too big alone is dropped, never retried.
* **replay:** a long error history puts the error id on its last chunk. When the history before an error was over about 1.8 MB and was cut into several segments, the error's id rode on the first one, and the player, which seeks to the end of the earliest segment that lists an error, landed 20 seconds or more before it. The id now rides on the last segment, the one that ends at the error.
* **replay:** an error `beforeSend` drops uploads no replay. The replay was told of an error before `beforeSend` ran, so in on-error mode every error the hook dropped (the README's `ResizeObserver` filter, or a consent gate) still uploaded the buffer, stored no error and left replays that no issue links to. The error still carries its replay id, but the recorder now hears of it only once the event is queued, for a hook that returns a Promise too.
* **replay:** an error before the recorder loads keeps the buffer rotating and its id. In on-error mode, an error captured while the recorder was still loading (or while the page waited for `load`) switched the recorder to post-error with an empty history, so the error's id was never listed in any segment, and the recorder then started without periodic checkouts: memory grew for the life of the page and the next error uploaded the whole history (10 minutes instead of 30 to 60 s). The recorder now decides on checkouts when it starts, not from the mode at boot, and an empty history is not uploaded: the pending ids ride on the post-error segment.
* **overseer, express:** events send only the user's `id` and `username` unless the new `sendDefaultPii` option is on. Every event carried the user object exactly as the app gave it (`setUser`, `initialUser` or Express's `extractUser`), so keys such as `passwordHash`, `sessionToken` and `ip_address` were sent, and Express's `errorHandler()` added `clientIp` to every error. Codmir keeps only the user's id and counts affected users by the id, else the email, else the username. By default an event now carries the `id` and `username` (the `email` only when there is no `id`), a user with nothing left is left out, and Express adds no `clientIp`; this also applies to Express's `extra.user`. With `sendDefaultPii: true` every key is sent except one that names a secret, and Express adds `clientIp`. `beforeSend` sees the user as it will be sent, and your own object is never changed. If you relied on `email` or `ip_address` being sent next to an `id`, set `sendDefaultPii: true`.
* **overseer, browser:** stack frames drop the query and fragment of a script URL. A frame kept the whole location, so an inline script or an inline `onclick` carried the page URL with its token, a loader such as `widget.js?key=...` kept its key, and each `?v=` cache-buster, dev-server `?t=` stamp or token made its own issue, in the culprit, the fingerprint and the agent prompt. A URL frame (`https://`, `blob:`, `webpack-internal:`) is now its origin and path, in parsed stacks, in the one frame a window `error` names and in `extra.filename`; plain paths, `node:` and `<anonymous>` are unchanged. Apps whose script URLs carry a query such as `?v=` get a new fingerprint once.
* **overseer:** secrets in error text, breadcrumbs and tags are scrubbed before sending. Only the keys of `extra` and breadcrumb `data` were checked, so `token=...` or `Bearer ...` in an exception message, `captureMessage` or console text, a breadcrumb message, a string under a harmless key or a tag value went out as written, and from there into the issue title. Those texts and tag values now lose cookies, JWTs, bearer tokens, `token=` style pairs, prefixed keys and query strings (before `beforeSend`, and before the fingerprint), tags under a secret key are dropped, and a transaction's name and tags get the same. Emails and IP addresses are not masked. An issue whose message held a secret gets a new fingerprint once.
* **express:** listeners on the request keep its scope, so users never mix. Behind a middleware that continues from a request or stream callback (multer, a body reader on `req.on('end')`, a pipe callback) the rest of the request ran with no request scope and no span: captures had no `request`, `setUser` set the process-wide user (one user's id landed on other users' errors and stayed set), and outgoing calls had no child span and no `traceparent`. `requestHandler()` now binds every listener added to `req` and `res` to the async context it was added in; `off`, `removeListener` and `once` work as before. New `bindToRequest(emitter)` does the same for another emitter a middleware creates during a request.
* **node, express, overseer:** a crash or a deploy no longer loses the queue. An uncaught exception, a crash outside a request and SIGTERM ended the process before the one-second send timer, so errors captured just before were never sent, and the README's crash snippet left a crashed process running (a rejection listener switches Node's exit off). The new `captureProcessErrors` option (off in `init`, on in `@codmir/sdk/express` unless `false`) captures an uncaught exception or unhandled rejection as `fatal`, mechanism `onuncaughtexception` or `onunhandledrejection`, not handled, flushes for 2 seconds at most and ends the process as Node would (exit code 1), and on SIGTERM and SIGINT flushes and ends the process by the signal; an app's own listener is left to decide, and `close()` removes the hooks. `close(timeoutMs?)` now returns a `Promise<boolean>` (`true` when the queue was sent within 2 seconds by default); callers that ignore the result work as before. The README's Node section is corrected. Express 4 `async` route rejections still do not reach `errorHandler()`.
* **nextjs, hono:** serverless hooks send the event before they return. `onRequestError` (`captureRouterError`) and, on a serverless runtime, `withCodmirTracing` and `withCodmirMiddleware` (option `flushOnEnd` overrides the detection) only queued the event, so a frozen function lost it; they now send it first (2 seconds at most), or hand it to Next's `waitUntil` when the request has one. Hono `codmirTracing` hands a failed request's send to `c.executionCtx.waitUntil`. New `flushRequestError()` for `captureRequestError`.
* **nextjs, overseer:** captures work in every server layer. Next.js bundles the SDK once for `instrumentation.ts` and again for each route, and only the copy that ran `init` had a client, so in a route handler `captureException` returned an empty id and sent nothing, `setUser` did nothing and `withCodmirTracing` recorded no transaction (only `onRequestError` worked, with no warning). Every function now finds the client another copy left in the global registry slot (a value there is used only when it is one of the SDK's own clients), `close()` empties the slot only when it holds that copy's own client, and the request scope's store, the active-span strategy and the tracing store live in `Symbol.for` slots, so a scope opened in one copy is seen by the others. `serverExternalPackages: ['@codmir/sdk']` stays an optional way to keep one copy.
* **react-native:** fatal crashes and unhandled promise rejections are sent. A fatal JS error was only queued before React Native's handler ended the app in a release build, so it was lost; it is now flushed (for 2 seconds at most) before the previous handler runs, and going to the background sends what is queued. On Hermes, unhandled promise rejections were never seen outside development builds; they are now captured as unhandled, with mechanism `onunhandledrejection`. JavaScriptCore has no such hook. Nothing is kept for the next launch.
* **overseer, browser, nextjs, remix:** a thrown value that is not an `Error` keeps its message, type and place. A plain object, an event or an error from another realm was turned into `new Error(String(value))`, so every plain-object throw landed in one issue titled `[object Object]` at the SDK's own line. Now a plain object is captured under its `message` and `name` (else `Object captured with keys: ...`) with a cleaned copy in `extra.thrown`, an `ErrorEvent` or rejection event gives the error or reason it holds, and an error from another realm keeps its type, message and stack. A stack made up for the value starts at your call to `captureException`, and a global handler's non-Error rejection has no frames (a window `error` has the one frame the event names). Issues from such throws group by their own message and place from now on: this is a one-time regroup for them; real `Error`s group as before.
* **overseer, browser, nextjs, remix, react-native, express:** a crash is sent as a crash. Every error the integrations capture on their own (a `window` `error`, an unhandled rejection, a server error, a React Native fatal, an Express `errorHandler` error) went out as handled, mechanism `generic`, level `error`, with `handled`, `mechanism` and `fatal` sitting in `extra`. The event now carries them: `exception.mechanism` is `{ type, handled: false }` with the integration's own type (`onerror`, `onunhandledrejection`, `server`, `nextjs-router`, `remix-handleError`, `remix-loader`, `remix-action`, `remix-server-render`, `global-error-handler`, `react-error-boundary`, `express-error-handler`), React Native's level is `fatal` when `isFatal` is true, and those three keys are no longer in `extra`. Your own `captureException` is unchanged: `generic`, handled, level `error`, and a `handled` or `mechanism` key you pass stays plain data in `extra`.
* **overseer:** a request that never answers no longer stops delivery. Every request now has a deadline (10 seconds in Node, 30 in a browser and in React Native); one that misses it is retried with the usual backoff and its events are kept, instead of holding every later flush for as long as the connection stayed open. The request is aborted where the runtime's `fetch` takes an `AbortSignal`, and the timer never keeps a process alive. `flush(timeout)` is unchanged.
* **overseer:** the context scrubber drops more secret keys and no longer passes class instances whole. Keys such as `apiKey`, `x-api-key`, `privateKey`, `credentials`, `pwd`, `auth`, `session`, `sid`, `jwt`, `signature`, `cardNumber` and `cvv` are dropped at any depth (`author`, `side`, `design` and `signal` stay), and a class instance or database document is cleaned through its `toJSON()` or its own properties instead of going out with a password hash; an `Error` is sent as `{ name, message, cause }` and a `URL` as origin and path. The log redactor and the scrubber now read their secret words from one list.
* **overseer:** tags and breadcrumbs set inside a request stay in that request. On a server `setTag`, `setTags` and `addBreadcrumb` were process-wide, so one request's tenant tag, or its `instrumentFetch` or Express `http.request` breadcrumb, landed on another request's errors, messages and transactions. Inside a request they now write that request's own state, as `setUser` does; an event carries the process-wide tags and breadcrumbs with the request's on top (its tags win, and the newest 100 breadcrumbs are kept). Outside a request nothing changes.
* **overseer:** a BigInt or a circular value in an event no longer stops sending. It crashed a Node process and held back every later event in a browser. A BigInt is now written as its decimal string and a value that is its own ancestor as `"[Circular]"` (the same object reached twice side by side is written twice); an event that still cannot be serialized (a `toJSON` or getter that throws) is dropped and `onDropped` hears `unserializable`, and every automatic flush is a handled call.
* **overseer:** events are sent under steady load. The flush timer was pushed back by every capture, so a client that captured at least once a second sent nothing for as long as that lasted, and once 1,000 events were queued the oldest, errors included, were dropped. The timer now starts at the first unsent capture and is never pushed back, so events leave at most one second later, and a full batch (100 events or the byte budget of a request) is sent at once.
* **overseer:** repeats of one error are capped. A render loop or a failing poll sent every copy of one error, and every stored event is billed. The new `rateLimit` option (default `{ perGroupPerMinute: 10, perMinute: 100 }`, `false` turns it off) lets through at most that many `error` and `message` events per rolling minute for one group (the event's own `fingerprint`, else the default one) and in all, after `beforeSend`; transactions are never capped. The rest are not sent and `onDropped` hears them as `rate_limited` (`status` 0), in one call a second at most and on `close()`.
* **browser:** a click on an `<svg>` or `<path>` no longer throws inside the SDK's own listener, so the SDK stops capturing that `TypeError` as an error of the app. The click is a breadcrumb again (`svg.icon`), with `data.class` as the class string; the click and input listeners never throw into the page.
* **overseer:** `beforeSend` is guarded. A hook that throws drops the event and `onDropped` hears `before_send`, instead of the error escaping into the app; a hook that returns a Promise is awaited and `flush()` and `close()` wait for it, instead of the Promise being sent as `{}`; and the hook gets copies of `user`, the breadcrumbs and `contexts`, so it can no longer change the app's user or the next event's breadcrumbs.
* **overseer:** one group per error whatever id its message holds. The fingerprint masks UUIDs as `<UUID>`, then runs of 8 or more hex characters that hold a letter as `<ID>`, then digits as `<N>`. Digits used to go first, so every UUID or mixed hex id made a group of its own; a digit-only number masks to `<N>` whatever its length. Groups whose messages hold such ids start again once under the new fingerprint.
* **package:** under `require` every entry point shares one client, one tracing context, one replay hook and one request scope, as under `import`. The CommonJS build bundled each entry on its own, so after `require('@codmir/sdk/express').init(...)` the root `captureException` sent nothing and `/tracing`, `/replay`, `/logs` and `/feedback` saw no client. The build now splits the CommonJS entries into shared `.cjs` chunks (tsup `--splitting`). Every `exports` path, the names `require()` returns and the names `import` finds in a `.cjs` file are unchanged; the whole CommonJS dist is 90 KB gzipped instead of 223 KB. An app that loads the SDK through both `import` and `require` still has two clients, one per format. CI runs `src/__tests__/dist-one-client.test.ts`: each case in a new Node process against the built dist and a local server, under both formats.
* **verify:** `verify()` succeeds only when the server took its event. It used to report "Connection verified" with no DSN and no key (0 requests) and after a 401. It now sends one message with a client of its own and reads the answer: it fails, with one sentence in `error` and in the failing step that names the server and the status (never the key, a query or a body), when there is no `clientKey`, the answer is 401 or 403, 402, 404, 429, another 4xx or a 5xx, the host can not be reached, nothing answers within `timeout`, the answer is not the ingest address's, the answer says the event was dropped (an unknown key, no card and no balance are named in words: the server answers 200 to those), or the config drops it (`enabled: false`, `sampleRate: 0`, `beforeSend` returning `null`). It no longer calls `init`, so the app's client, its tags (`source=sdk-verify` and `sdk_version` went out with the app's later events), queue, breadcrumbs and replay are untouched, and it leaves no timer, listener or client behind. `printVerifyResult` prints `[FAIL]` and the sentence; `quickVerify(key, config?)` takes an optional config, and `quickVerify(dsn)` is `false` since a DSN has no key.
* **overseer:** `flush(timeout)` uses its argument: `true` when everything queued was sent or refused, `false` when the time ran out first (the sending goes on). Each caller has its own time, the timer is unref'd and cleared, and a late answer is no unhandled rejection. Without an argument it behaves as before.
* **express, hono, nextjs, remix, overseer:** each request has its own user. Express's `extractUser` called the process-wide `setUser`, so an event captured in one request's async tail could carry the user of another request that ran meanwhile (only `errorHandler`'s own capture was right), and the same held for any `setUser` an app called in a handler. The request scope now holds a user: inside a request an event's user is what `extractUser` answered (`null` or `undefined` means nobody, not the process-wide user) or what `setUser` was last called with in that request, and `setUser` inside a request leaves the process-wide user and the other requests alone. Outside a request `setUser` is process-wide as before; a request with no user of its own takes the process-wide one. Express calls `extractUser` once per request and again in `errorHandler` only when a later middleware has set `req.user`; an `extractUser` that throws no longer breaks the request (it threw out of the middleware before) and leaves the request without a user; `tracingHandler` shares the request's scope instead of opening a second one. Remix's `withCodmirTracing` and `withCodmirRequestHandler` now run the handler in a request scope too, so its errors carry `request.url` (origin and path) and `request.method`. The README lists which integrations keep the scope across `await` and where `setUser` is still process-wide (a handler that is not wrapped).
* **replay:** a picked radio button or checkbox is no longer recorded. rrweb stores `checked` in a snapshot and an added node and sends `isChecked` and the input's own `value` in an input event, whatever the input mask. With the default privacy (`maskAllInputs`), or with `radio` or `checkbox` in `maskInputTypes`, `checked` is taken off such a node (any case of the tag and the type, a node in an iframe or a shadow root too), a change of that attribute is dropped, and its input events and clicks are dropped whole. A `select`'s `selected` option is not recorded either. The node's `value`, `name` and label stay. The recorder keeps at most 50,000 ids to know the types and, beyond that, treats every input as hidden. With `maskAllInputs: false` and the type not named they record as before. The README lists what a recording holds and what it does not cover (custom `role="radio"` controls, `contenteditable`, the pointer's path).
* **replay:** CSS keeps no part of the page's query. rrweb resolves a relative `url(...)` against the page's address cut at its last slash, so `background: url(#bg)` on `/a/b?next=/x/y&token=abc/def` was recorded with `?next=/x/y&token=abc/` inside it, in a style attribute, a `<style>`, a stylesheet rule, an adopted stylesheet and a style declaration. The query is now cut there too, as it already was in links and sources; an absolute address of your own with a query of its own, and data URLs, stay.
* **browser, nextjs, express, remix, react-native:** `init` after `close` starts a new client. The entries set a flag in `init` and never reset it, so after `close` a later `init` was ignored: no client, no listeners, no config. Each entry's `close` now ends what its `init` started (the flag, the error and rejection handlers, the click and input breadcrumbs, the route breadcrumbs, the `console.error`, `fetch`, XHR and `history` patches, the pageload and navigation transactions, React Native's global error handler) and then closes the client, so a second `init` has one of each and its own config. `init` twice without `close` is still ignored. A patch another library, or a second copy of the SDK, put over one of ours is no longer taken off: it stays in place, passes every call on and records nothing, so two copies may close in either order. An error captured after `close` and before the next `init` is sent once, without retries, as before. The self-healing patch runtime no longer starts a timer or an observer when it was stopped while it loaded its manifest.
* **browser, nextjs, remix, react-native, tracing:** nothing throws where `window` exists and has no `location`, `history`, `document` or `addEventListener` (React Native sets `global.window = global` in 0.72 and defines `globalThis.window` in 0.88; a worker has no window). Without a location there is no navigation breadcrumb, no page context in an error and no pageload transaction; the pageload tracing, the route breadcrumbs, the self-healing patch runtime and the global handlers each check what they read. A `dsn` that is given is used as it is. The `/browser` case of `api-key-alias.test.ts` ran in the node environment, where `init` returns at once, and passed through a client an earlier case left; it now runs in jsdom.
* **logs:** a Vercel log drain's records are read as Vercel documents them. `statusCode: -1` is 500 (or the status the visitor got, `proxy.statusCode`), `proxy.statusCode: -1` is a revalidation and counts no request, a request counts once per `requestId` (with the worst status its records gave) however the records are fed, the path and method are the proxy's first, firewall and build records count nothing, and the platform's own lines (`START`, `END`, `REPORT`, `INIT_START`, an invocation's summary, its `report` and `metrics` records) are no text of the app. A record may give a request and a text. `RequestRecord` has an optional `replaces`, `parseLogLines` an optional third argument that carries the ids.
* **logs, overseer:** a finding the server did not take is sent again. With `cloud.apiKey` a finding that was refused (401, 402, a limit, a `droppedEvents` entry, or a queue that gave up) goes out again with its next hit, all its hits with it, a restart too, and its place in `perDay` is given back; after a refusal nothing is sent for 1 minute, doubled per refusal in a row up to 60 (`stats().cloud.pausedUntil`). The client's `onDropped` gets an optional `eventIds`, and is also called, with `status` 0, for events the client gave up on (a full queue, a closed client).
* **logs:** a release or a service keeps its name. The monitor took `web@1.4.0` for an email address, a commit for a hex secret, `dpl_…` for an id and a date stamp for a number, so every release of an app had one name and the platform could not tell the fix from the next release; `projects-production-checkout-worker-us-east-1` became `[secret]`. A name now stays when it is a commit, a version, `name@version`, `main-<commit>`, a date stamp, an epoch or plain words, and is dropped (no `release`, no `service`) when it holds an email address, an IP address, a JWT, a token, a `key=value` pair or a match of the app's own `redact` patterns. A saved state an older version wrote with `[hex]` in it loads, without those names. The prefixed secrets have their own form (`sk_`, `ghp_`, `npm_` + 20, `AKIA` + 16 and so on), so `skipped_records`, `skeleton-loader` and `npm-mirror-service` are no longer masked in log messages and no longer merge groups.
* **overseer, report, client:** the default addresses are on `https://www.codmir.com`. They were on the apex, which answers every request with a redirect: a browser refuses a redirect on the preflight `x-overseer-key` makes it send, so a page without its own `dsn` sent nothing, and `fetch` drops `Authorization` when a redirect leaves the host, so bug reports and the API client were never signed in. The default `dsn` is `https://www.codmir.com/api/v1/overseer`; a `dsn` you set is used as before.
* **package:** `sideEffects` is `false`. No module of the SDK does anything when it is imported, so a bundler may drop any chunk nothing uses. The old value marked every `dist/chunk-*` file as having side effects, which kept the API client's zod schemas, and zod, in an esbuild browser bundle of `import { init, captureException } from "@codmir/sdk"`: 80.8 kB minified, now 20.5 kB. CI now checks that every entry except `/express`, `/hono`, `/nextjs/server` and `/remix/server` bundles for the browser with esbuild and vite without reaching a Node built-in, and that a Next.js app importing `@codmir/sdk/nextjs` in a client component, `app/error.tsx`, `pages/_app.tsx` and an `instrumentation.ts` next to a middleware builds.
* **security:** breadcrumbs and the pageload transaction no longer carry a URL's query string or fragment. `fetch` and `XHR` breadcrumbs (message and `data.url`), the Next.js and Remix navigation breadcrumbs (`from`, `to`, the referrer and the `pushState`/`replaceState` target) and the pageload/navigation transaction's `data.url` keep origin and path only, so an `?access_token=` or an OAuth `#access_token=` no longer reaches Codmir with every error.
* **security:** an error report no longer carries the request's headers, cookies, authorization, query string, route params or body. Next.js `captureRequestError` sent every header; Express and Remix sent headers (minus a short list), the query and params; all of it went into `extra` and some into breadcrumbs. The integrations now send only the event's `request` (origin, path, method) and a `route` pattern. The core also cleans `extra` and breadcrumb `data` at `captureException`/`addBreadcrumb`: a `Request`/`Headers` value, a request-like object, and any key named like a request part or matching cookie, authorization, token, secret or password are dropped, so a future integration cannot bring the leak back. Express's `captureRequestBody` option is deprecated and ignored.
* **overseer:** stack traces parse V8 frames without a function, `async` and `new` frames, eval and native frames, and Firefox and Safari `fn@file:line:col` frames; `in_app` is false for `node_modules`, Node internals and the SDK's own files.
* **overseer:** a batch stays under the 256 KB the server takes. A request carries at most 240000 UTF-8 bytes as well as 100 events; an event too big on its own loses its oldest breadcrumbs, or is reported to `onDropped` as `too_large`; and a 413 halves the batch instead of dropping it. 100 events with many breadcrumbs used to go over the cap, and the 413 dropped all of them.

* **overseer:** errors now reach Codmir. Each error is sent as the `{type:"error", event, group}` wrapper the server stores, with a fingerprint computed like the platform's, instead of a flat event that was dropped behind a 200. Failed sends (non-2xx, network) are retried with capped exponential backoff and a bounded queue, `droppedEvents` is logged in debug mode, a browser flushes with `keepalive` on `pagehide`/hidden, and the default endpoint is always `https://codmir.com/api/overseer` rather than the page's own origin.
